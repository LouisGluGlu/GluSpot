# HomePod touch control and native queue investigation — 2026-10-18

Scope: read the current sender/owned-player boundaries and upstream implementations without opening a receiver session, inspecting an Apple account or controlling a physical HomePod. The follow-up implements only the existing authenticated AirPlay 2 play/pause button return path. Native HomePod queue retrieval and queue injection remain unimplemented.

## Conclusions and evidence

| Capability | Evidence | Decision |
| --- | --- | --- |
| A HomePod button can control its current GluSpot source | OwnTone's AP2 event parser accepts `type: sendMediaRemoteCommand`, `value: paus` or `play`; its handler toggles the source's current play state for either value. GluSpot already decrypts this same authenticated `/command` channel but previously ACKed and discarded those messages. | Reuse the existing connection and owned-player toggle. No Apple ID, new pairing credential, HTTP listener or extra network session is needed. Physical touch behavior on the user's firmware still needs hardware verification. |
| Legacy DACP reverse control | GluSpot sends `DACP-ID` / `Active-Remote` headers but has no `_dacp._tcp` service or `ctrl-int` server. These headers alone do not implement reverse control. | Do not add a second command server when the authenticated AP2 channel already carries the required button. |
| Read native HomePod metadata / queue | pyatv implements an MRP tunnel over AirPlay 2, explicitly selects transient credentials for `AudioAccessory` HomePods, requests MRP client updates and consumes `SetState.playbackQueue`. Its existing artwork queue request deliberately asks for just one item. | There is a plausible account-free protocol path, but no evidence from this GluSpot session that it yields a complete native queue, that every HomePod firmware returns it, or that it can be added alongside this sender without affecting audio. Do not display GluSpot's local queue as HomePod's native queue. |
| Inject arbitrary tracks into HomePod's native queue | pyatv's reverse-engineered protobuf schema names `SetPlaybackQueue`, `InsertIntoPlaybackQueue` and opaque `systemAppPlaybackQueueData`; the inspected implementation does not provide a verified arbitrary audio-URL-to-native-queue workflow. | Do not infer an implemented API from enum names. No native queue write is shipped. This investigation does not establish that such a feature is impossible; its required payload, device support, accepted content and playback authority are unverified. |

The external evidence is implemented upstream interoperability code, not a published Apple protocol contract. It supports a scoped implementation and a candidate research path; it does not establish a general HomePod API guarantee.

## Implemented ownership and lifetime

1. The optional `RaopEvents.receiverPlayPause` callback recognizes only exact string values `paus` and `play` in an authenticated binary-plist `POST /command` while the sender is streaming. A canonical numeric CSeq is required. Each sender retains at most 64 accepted CSeq values; retransmissions still receive the original minimal encrypted 200 ACK but do not toggle twice. Existing volume updates and unknown-message ACK behavior remain intact. The callback fires after the ACK is queued.
2. Only the owned direct-PCM group host registers useful output for these callbacks. The system-capture path receives no player-control bridge. Both one HomePod and multi-output owned playback already use this group host.
3. The callback only appends to a per-member queue of at most eight items. The host discards items older than two seconds and does not publish them for unarmed, uncommitted, retiring or changing memberships. Published events contain the exact receiver ID, PCM epoch and membership revision.
4. The owned process rejects events from a superseded child state, old PCM epoch, nonmember, unconfirmed membership, terminal process, invalid sequence or invalid age. The controller checks the current feeding epoch, receiver transport, membership revision, media token, freshness and a bounded 128-key duplicate window.
5. The existing bridge queues the operation onto the Qt owner thread with cancellation, a media token and an absolute expiry. The Qt slot rechecks the direct session, receiver authority and deadline before calling the existing `send_playback_command("toggle_play_pause")`. No receiver reconnect, seek, volume adjustment or queue replacement is added.

## Verification and remaining hardware work

- Pure controller/process verification: 31 tests passed. Coverage includes duplicate taps, unsupported commands, old child/epoch/revision/member, pending memberships, superseded tracks, terminal batches, nonfinite/expired timestamps, bounded retention and reader timestamp authority.
- Native encrypted sender and group regressions: the final `packaging/windows/build-airplay.ps1` run rebuilt successfully and passed all 12 native suites in 109.40 seconds. The sender policy suite covers authenticated fragmented/coalesced events, encrypted ACK ordering, preserved volume events, canonical CSeq deduplication, unsupported commands, invalid sequence/value types, corrupted ciphertext and a fresh authenticated session. Group checks cover bounded retention, expiry and ineligible-member discard. Tests use the existing independently keyed fake receiver, not a physical HomePod. Log: `logs/homepod-control-native-final3-2026-10-18.log`.
- Qt bridge verification: all 67 tests in `tests.test_owned_audio_outputs` and `tests.test_owned_audio_bridge_handoff` passed in 7.202 seconds, without Qt callback tracebacks. The serialized run covers exact session/membership authority and a tap expiring while the GUI request waits. Log: `logs/homepod-control-qt-2026-10-18.log`.
- No receiver session, Apple account, local queue probe or acoustic test was performed. A physical follow-up should check one tap pauses and another resumes for both HomePod-only and HomePod-plus-local playback, paused duration beyond the receiver watchdog window, and taps during song/member changes. It must also check that all existing outputs remain selected and the native session is retained. These are pending checks, not claimed results.
- Further queue exploration needs a read-only MRP session against a known selected device, capability/response inspection, bounded queue pagination, and comparison against the actual Home app queue. Queue injection needs a verified content/payload contract and evidence of receiver acceptance; it is not hidden behind a local simulated list.
