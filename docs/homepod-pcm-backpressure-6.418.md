# GluSpot 6.418：HomePod 同步输出拥塞断连

日期：2026-10-23。基线 `17b3ccb`（6.417），分支 `codex/homepod-pcm-backpressure-6.418`。

## 故障证据

用户在 6.417 安装版中观察到，HomePod 播放约 90 秒后断声并退出已连接列表，播放器继续运行。故障后的导出记录显示，实际停止的那轮会话持续 70.109 秒，`pcm_error` 为 `backpressure`。最后一次统计中的 34 次接收端保活全部成功，两个加密事件均已应答，没有解密错误或原生捕获丢包，随后是本地主动停止。90 秒不是协议中固定的断连时限。

同一运行现场另有一条主线程卡顿记录：MyDockFinder 原生窗口检测停顿约 2.59 秒。这是需要继续调查的上游卡顿，不能仅凭栈快照确定其全部原因。原始诊断含设备标识和本地路径，仅保留在用户本地，不进入源码仓库。

使用真实 Qt 解码、现有命名管道、原生发送器和独立本地加密 AP2 接收器，注入 2.6 秒 GUI 停顿，修复前在约 5.64 秒复现 `Direct PCM queue overran`。另一条独立回归证明：一秒音频拆成 100 个 10 ms 缓冲块时，第 65 块就触发 Python 的 64 块上限，尚未达到原有音频字节预算。

## 修改

- Python 按音频字节数限制待发量，取消较小缓冲块会提前耗尽的 64 块限制。将待发音频预算明确设为四秒／705,600 字节，以容纳本次测得的 2.59 秒回调集中到达。新增队列高水位及失败类别诊断，不记录音频内容。
- 原生命名管道保留暂时无法写入环形缓冲的完整数据包，等待下游释放容量。停止和父进程退出可以打断等待；两秒没有腾出容量仍按错误结束，持续故障不会无限缓存。
- 协调器只向共享 conditioner 移入其剩余容量允许的 PCM；其余数据留在有界环形缓冲和管道中。所有输出继续共享相同、有序的源帧，不丢弃音频或给设备独立改写时钟。
- 保留 provider 边界、原有鉴权、保活、音量、静音归属和源／会话隔离。四秒是最大待发缓存，正常播放不会主动填满它，也不是新增固定输出延迟。

## 验证

- 修复前的短缓冲块回归确实失败于第 65 块；修复后通过。
- 修复后的实际 Qt／命名管道／AP2 接收器连续运行 **180.015 秒**，在第 95 秒注入 **2.6 秒** GUI 停顿，保持同一发送进程和连接，接收端音频包顺序及解密正常，没有捕获丢包。待发队列高水位 **425,984 字节**，低于 705,600 字节上限；结束时已排空。
- **12 项原生测试／56.68 秒通过**。新增真实管道满缓冲后的恢复、PCM 顺序及满缓冲取消检查，保留持续堵塞超时和进程身份检查。
- Python 定向回归当前 **56 项通过**；包含四秒字节上限、错误证据保留、旧会话隔离和停止清空。

完整 Python 回归及 6.418 安装／便携包验证正在进行。首次受限环境的完整回归停滞；本地套接字测试也曾返回沙箱权限错误 10013，移出网络限制后 30／30 项套接字检查通过。失败尝试保留在 ignored 日志中，不计入通过结果。

## 验证边界

以上持续播放使用静音合成音频和本地协议接收器，不能代替物理 HomePod 听感、无线网络或长时间硬件验收。突发供音可能暂时增加排队延迟；缓冲始终有界，持续供音故障仍会退出并恢复程序内输出。MyDockFinder 2.59 秒卡顿的根因和所有来源的长时间播放仍需跟进。

本轮尚未替换用户的已安装程序。旧版 6.417 及其 Release 保留。
