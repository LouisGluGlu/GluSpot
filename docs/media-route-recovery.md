# Media lookup and output recovery

The media provider now retrieves NetEase search metadata through the form POST cloud catalog endpoint. The former web-search endpoint returned a successful response whose `result` was a string rather than the expected song object. Artwork lookup failed to parse it, while lyric lookup fell through to slower alternative services. Song identity, artist, recording version, album and duration checks remain in place. The cloud catalog's `ar` / `al` fields are accepted by the existing lyric candidate matcher.

New lyric requests use section versions `-1`, including `lv`, `kv` and `rv`. Sending version `1` incorrectly declares that the client already holds that section; a version-1 song can then return a successful response with empty lyrics. This change requests actual current source content, without manufacturing word timestamps.

An explicit failed artwork lookup ends the repeating download ring and lets acquired lyric feedback proceed. The best available thumbnail remains softly rendered; failure does not claim that it became a high-resolution original. A later pending retry starts the ring again. A decoded original finishes normally. For the same NetEase artwork object, a completed upgraded URL also counts as acquisition complete when the source returns a smaller native image than requested; the sharper cached variant remains selected instead of looping forever because the downloaded bytes differ.

## Output ownership and recovery

Temporary application-output changes remain confined to exact held music process identities and their Console / Multimedia policies. System default devices, unrelated applications, communications policies and endpoint volume are outside this recovery transaction. A user's newer application policy is preserved.

When the original output disappears, restoration returns the owned temporary binding to the currently verified default. A previously default-following source also follows a default chosen while the group was running. The temporary policy is returned even when live playback proof fails; durable recovery evidence remains for retry. Losing an active audio session after unplugging does not erase the saved process ownership. An enumeration failure cannot strand the temporary pin: known owned policy values are returned without guessing an output, while actual playback proof stays pending. The controller retries incomplete cleanup after the helper has stopped.

An already returned-policy observation whose complete saved process identities have exited can be retired without reading or changing a replacement PID's policy. Records with outstanding writes retain their normal recovery requirement. Explicit site repair can preserve a dead-owner record in a separate backup before beginning a newly authorized music transaction; this is a diagnostic operation, not automatic cleanup or a global audio reset.

`prepare_default_follow(source)` and `guard.follow_system_default()` are explicit music-app repair operations. They reuse held identities, rollback and actual migration proof, while allowing other applications to share the current Windows default. The default is rechecked throughout preparation, role writes and migration. They open no capture stream and suppress no output. Ordinary group preparation still requires an unoccupied spare capture source; the shared repair path does not weaken that contract.

These are network samples, not promised load times.

The user confirmed normal audible playback. Windows defaults and endpoint volumes were unchanged; Realtek remained zero and AirPods remained approximately 67%.
